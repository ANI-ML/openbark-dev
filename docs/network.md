# Network calls

OpenBark is local-first (master prompt §3, rule §7.4). This file lists every network connection the software can make. **A host that isn't listed here is a bug.** CI enforces this in two ways:
- the offline end-to-end test runs the full pipeline with networking disabled;
- the source check (`scripts/ci/check-network.sh`) confirms that `os-models`, `os-sync` and `os-connect` are the only engine crates with an HTTP client; that only `os-sync` (the device's hub client) and `os-hub` (the clinic hub's listener) have a TLS stack; that only `os-hub` has an HTTP server for other machines and only `os-server` one for this computer (loopback); that only `os-sync` and `os-hub` use mDNS; and that sockets appear only in those crates' source. `os-sync` makes the encrypted sync calls (L2 and L3 below, ADR-0029; and R12 and R13 until ADR-0029 phase D retires them), and only once the person turns sync on. `os-hub` listens only while hub mode is on (L1). `os-connect` makes the Twilio REST calls (R9 below, ADR-0023);
- the phone bundle check (`scripts/ci/check-phone-bundle.mjs`) confirms that no Twilio code reaches the main window and that the main window's Content-Security-Policy allows no remote host. Only the phone window may reach Twilio (R10).

### The clinic hub, on the local network (ADR-0029)

All off by default, and only in builds that offer encrypted sync (the preview gate: builds made with `OPENBARK_SYNC_PREVIEW`, or a run with `OPENBARK_SYNC_PREVIEW=1`; release installers have neither). Nothing here reaches the internet or ANI.ML: the hub is a computer of the clinic's own.

| # | When | Where | What's sent | Purpose | Off switch |
|---|---|---|---|---|---|
| L1 | Only while **Make this computer the clinic hub** is on (Settings, Clinic hub; desktop builds only, never on a phone) | **Listens** on one TCP port on every interface (default 47110, a setting), IPv4 and IPv6. A connection from an address outside the allowed ranges (default: this computer's loopback, RFC 1918, link-local, IPv6 unique local addresses and 100.64.0.0/10; a setting) is closed before the TLS handshake | TLS 1.3 with the hub's self-signed certificate (made once, kept sealed in the hub's folder). L4 (later, ADR-0029 section 7): the sync folder, which is file access by the hub, not network access by OpenBark.

Encrypted sync is **off by default**: with it off, OpenBark makes none of the L2 browsing, L3, R12 or R13 calls. ADR-0017 drafted these rows as R6 to R8; R6 went to the MLX engine pack (ADR-0025), and R9 to R11 are taken or reserved by ADR-0023, so sync uses R12 and R13, with R14 kept for Realtime (later in M3). Public wording: "Recordings and notes stay on your devices unless you turn on encrypted sync. Even then, only encrypted copies leave, and our servers can't read them."

Removing models or engine packs, adding a model from this computer, and saving or removing the Hugging Face token in the keychain make no network calls. (Checking a token when it is saved is the single `whoami-v2` call in R4.)

### Calls through the clinic's own Twilio account (ADR-0023)

**Off by default, clinic-owned account.** Nothing below happens until a veterinarian connects the clinic's own Twilio account in **Settings > Phone calls** and turns the phone on. The clinic pays Twilio directly. ANI.ML runs no relay or token server, holds no keys and pays nothing. This release makes outgoing calls only. R6 to R8 are reserved by ADR-0017.

| # | When | Host(s) | What's sent | Purpose | Off switch |
|---|---|---|---|---|---|
| R9 | Only when a veterinarian chooses **Connect** or **Check setup** in Settings > Phone calls | `api.twilio.com` (HTTPS), under `/2010-04-01/Accounts/<the clinic's account SID>/` | Basic auth with the clinic's API key SID and secret; the secret goes to no other host, and redirects aren't followed. **Connect:** lists one TwiML App to check the key (`GET Applications.json?PageSize=1`), lists the account's numbers and verified caller IDs (`GET IncomingPhoneNumbers.json`, `GET OutgoingCallerIds.json`) to check the caller ID, finds the "OpenBark" TwiML App (`GET Applications/<sid>.json`, or `GET Applications.json?FriendlyName=OpenBark`) and creates it or sets its Voice URL to the clinic's outgoing Bin (`POST Applications.json` or `POST Applications/<sid>.json`). **Check setup:** the key check, the caller-ID lists and the app read. `User-Agent: OpenBark/<version>`. Nothing about patients | Set up and check the clinic's own Twilio account | Don't connect Twilio, or **Disconnect** |
| R10 | Only from the phone window (`phone.html`), and only while a call is being placed or is on | `wss://voice-js.roaming.twilio.com/signal` (signalling, TLS on TCP 443), then, if the connection has to be made again during the call, the edge Twilio chose: `wss://voice-js.<edge>.twilio.com/signal`, where the edge is one of `ashburn`, `umatilla`, `dublin`, `frankfurt`, `sao-paulo`, `sydney`, `singapore` or `tokyo` (the phone page's policy allows exactly these); `https://eventgw.twilio.com`, or `https://eventgw.us1.twilio.com` (or `ie1`, `au1`) once Twilio names the account's home region (call-quality events); media as SRTP over UDP to Twilio's media servers in 168.86.128.0/18, ports 10000 to 60000, at the addresses Twilio's signalling gives | An access token minted on this computer, valid for one hour (never the API key secret). The number dialled. The call's audio, as on any phone call. Call-quality events (call state, round-trip time, jitter, packet loss; no audio), which go to Voice Insights in the clinic's own Twilio account; the SDK's public options can't turn them off. The SDK's sounds are local files (`apps/desktop/public/phone-sounds`), so `sdk.twilio.com` isn't contacted | Make calls through the clinic's own Twilio account | Turn the phone off (Settings > Phone calls), or don't connect Twilio. Recording and transcription stay on the computer |

- The recording is made on this computer. OpenBark never asks Twilio to record: the outgoing Bin has no `record` attribute.
- Nothing listens. Calls go out over R10's outgoing connections only.
- A clinic firewall must allow UDP from the computer to 168.86.128.0/18 on ports 10000 to 60000. Twilio's relay for networks that block UDP (its Network Traversal Service) is billed separately and isn't used.
- Twilio carries the call like any phone company and keeps call logs (numbers, times, durations) in the clinic's account, in the United States (Twilio has no Canadian region).
- The main window reaches no Twilio host: its own `<meta>` Content-Security-Policy allows only this computer (web mode sends the same rule as a header). The phone page's policy adds exactly the R10 hosts above.
- `OPENBARK_TWILIO_API_BASE` points R9 at a local stand-in for tests and demos. Only debug builds and builds made with the `mock-twilio` feature read it (never the builds clinics get), and only a loopback address is accepted.
- Both web-mode policies allow WebSockets to this server's own port only.

The install scripts (`install/`) make no calls of their own: building from source uses B1, B2 and B3, and `-Models` / `--models` uses R1 and R2. Uninstalling makes no network calls.

The Windows setup wizard makes one call, and only on a computer without Microsoft Edge WebView2 (Windows 10 and 11 almost always have it): it downloads Microsoft's WebView2 bootstrapper from `go.microsoft.com` (redirecting to `msedge.sf.dl.delivery.mp.microsoft.com`), which installs WebView2 from Microsoft. Nothing about the clinic is sent. The macOS disk image and the Linux packages make no calls.

Nothing else at run time:
- no telemetry, analytics, crash reporting or update checks;
- no licence server;
- no fallback to a cloud model.

Transcription, note generation and everything else run with the network unplugged once the models are on disk.

## The website (not the app)

The public website, www.openbark.io, is separate from the software above. It has an account portal (`/portal`, ADR-0017) where a visitor can sign in with an emailed code, keep a short profile (name, clinic, role, country, update emails), find the downloads and delete the account. Since ADR-0028 it also runs clinics: create one, invite people, accept an invite or join with a code, and, for admins, a dashboard of the daily usage counts members choose to share. **The website makes these calls, in the visitor's browser. The OpenBark app makes none of them:** it ships no Supabase SDK and no portal code. The app's own Supabase calls are R12 and R13 above, made from Rust, and only once encrypted sync is turned on.

- Opening the portal signed out sends nothing to Supabase. The website end-to-end test checks this, and answers every Supabase call in its own mocked sign-in, so tests never reach the live project.
- The sign-in session is kept in the browser's localStorage (`sb-nmecovtmijnfnjuadicp-auth-token`), as supabase-js does by default. The site sets no cookies.
- No realtime connection (`wss:`) is opened; the CSP doesn't allow one.
- Every page also fetches `release.json` from the site itself and the Manrope and JetBrains Mono fonts from Google Fonts.

### CI and release signing (ADR-0020)

Contacted only by the release workflow on a pushed `v*` tag, and only for a platform whose signing secrets are set (`scripts/ci/signing-plan.sh`). Manual runs and local builds contact none of these. The self-test workflow (`signing-selftest.yml`) contacts only the timestamp servers, with throwaway certificates. What leaves the runner is a file digest, a sign-in token or the finished installer for Apple's notary service, never anything about a clinic.

| # | Host(s) | Purpose | Notes |
|---|---|---|---|
| C1 | `login.microsoftonline.com` | Windows: `azure/login` exchanges GitHub's OIDC token for an Azure token (no stored Azure secret) | Federated credential limited to `repo:ANI-ML/openbark-dev:environment:release`, the development repo where releases are built |
| C2 | `eus.codesigning.azure.net` (the `AZURE_SIGNING_ENDPOINT` variable) | Windows: Microsoft Artifact Signing signs each file's SHA-256 digest. The files themselves never leave the runner | East US; there is no Canadian region |
| C3 | `timestamp.acs.microsoft.com` | Windows: RFC 3161 timestamp on every signature (Artifact Signing certificates last three days, so a timestamp is required) | Also used by the self-test's throwaway certificate |
| C4 | `api.nuget.org` | Windows: downloads `Microsoft.ArtifactSigning.Client` 1.0.128, checked by SHA-256 in `scripts/ci/windows-signing.ps1` | Pinned version and hash |
| C5 | `timestamp.apple.com` | macOS: `codesign` adds Apple's secure timestamp to Developer ID signatures | Also contacted by the self-test |
| C6 | `appstoreconnect.apple.com` (notarytool's API; believed) | macOS: Tauri and `scripts/macos-dmg.sh` upload the app, the uninstaller and the disk image for notarization, then wait for the result | Uses the App Store Connect team key. Stapling fetches the ticket from Apple's CloudKit service (host to confirm on the first signed run) |

Linux and checksum signing (OpenPGP) is offline: the key is used on the runner and nothing is contacted.

Users' computers: OpenBark itself never calls a signing or certificate service. Windows and macOS may check a signature, a certificate's revocation or notarization online on their own when the app is installed or first opened. That is the operating system, not OpenBark, and it happens with or without signing.
